# Porpoise Tool

Porpoise Tool is an annotated PowerPC assembly-to-C frontend for main/DOL-style GameCube title code. It emits lifted C functions, a small PPC execution-state shim, a Meson static library, and—when an entry point is available—a `DolphinMain` adapter for use with `libPorpoise`.

This project does **not** claim complete PowerPC ISA support, 100% correctness, or production readiness. Every accepted instruction receives a measured status in `porpoise-report.json`; an instruction being lowered is not evidence that all of its hardware semantics have been verified.

## Scope and dependency boundary

Porpoise Tool owns assembly parsing, instruction lowering, PPC register state, typed ABI bridges, and generated-project layout. `libPorpoise` owns SDK implementations, console memory, host startup, graphics, input, and the rest of the PC-port environment.

`libPorpoise` is consumer-supplied and still evolving. It is not vendored, pinned, downloaded, or generated by this tool, and many of its subsystems are not ready for general use. Version-sensitive host calls are confined to the generated adapter.

Current scope:

- annotated `.s`/`.S` input representing main/DOL-style title code;
- Windows through MSYS2/MinGW-w64 and Linux through GCC;
- Meson for Porpoise Tool and generated projects;
- generated static libraries and an optional title executable;
- explicit typed import/export declarations through a versioned ABI manifest.

Out of scope:

- reading a `.dol` binary directly;
- REL or native-module generation;
- a standalone SDK/CRT implementation or a second console-memory runtime;
- automatic guessing of external SDK function signatures;
- macOS, MSVC, or other untested host toolchains.

## Build Porpoise Tool

Requirements are Meson 1.2 or newer, Ninja, Python 3, and a GCC-compatible C compiler. From a Linux shell or an MSYS2 MinGW64 shell:

```sh
meson setup build --buildtype=release
meson compile -C build
meson test -C build --print-errorlogs
```

The executable is `build/porpoise` on Linux and `build/porpoise.exe` on Windows.

To smoke-test generated output against a local, consumer-supplied `libPorpoise` checkout, opt in at configure time:

```sh
meson setup build -Dlibporpoise_compat_path=/path/to/libPorpoise
meson test -C build --print-errorlogs
```

The default test suite uses an in-repository contract stub and does not require or modify a working `libPorpoise` checkout.

## Command line

```text
porpoise INPUT --output DIR [--config FILE] [--abi FILE]
         [--skip-list FILE] [--entry SYMBOL] [--force] [--strict]
         [--quiet | --verbose]
```

`INPUT` is one annotated assembly file or a directory recursively scanned for `.s` and `.S` files. `--output` is always required. A directory input containing no assembly files is an error.

| Option | Behavior |
| --- | --- |
| `--output DIR` | Required destination. An existing nonempty directory is protected unless `--force` is present. |
| `--config FILE` | Load only this explicit schema-version 1 config. Nothing is auto-loaded beside the executable or input. |
| `--abi FILE` | Load the typed import/export manifest described in [ABI_MANIFEST.md](docs/ABI_MANIFEST.md). |
| `--skip-list FILE` | Skip exact input function symbols listed one per line. `#` begins a comment. Unknown symbols are errors. |
| `--entry SYMBOL` | Select a translated function for the generated `DolphinMain`. |
| `--force` | Atomically replace an existing nonempty destination after generation succeeds. This is CLI-only. |
| `--strict` | Reject approximate instruction lowerings instead of recording a warning. |
| `--quiet` | Suppress success, progress, and non-error diagnostics. |
| `--verbose` | Print scanning, ABI-loading, and generation progress. |
| `-h`, `--help` | Print help; it must be used by itself. |
| `-V`, `--version` | Print the version; it must be used by itself. |

Duplicate options, extra positional arguments, unknown options, and using both `--quiet` and `--verbose` are rejected. CLI paths are interpreted by the invoking environment; paths supplied by config are resolved relative to the config file.

### Configuration

Configuration is a strict, flat JSON object. `schema_version` is required and must be the number `1`; all other keys are optional:

```json
{
  "schema_version": 1,
  "abi": "title-abi.json",
  "skip_list": "skip-functions.txt",
  "entry": "main",
  "strict": true,
  "verbosity": "normal"
}
```

Allowed keys are exactly:

- `schema_version`: numeric `1`;
- `abi`: nonempty path string, relative to the config file when not absolute;
- `skip_list`: nonempty path string, resolved the same way;
- `entry`: nonempty function-symbol string;
- `strict`: JSON boolean;
- `verbosity`: `"quiet"`, `"normal"`, or `"verbose"`.

Unknown keys, duplicate keys, nested values, wrong types, and empty strings are rejected. `INPUT`, `--output`, and `--force` cannot be set in config. Command-line values override their config counterparts; `--strict` enables strict mode and there is no CLI switch that disables config-enabled strict mode.

### Exit codes

| Code | Meaning |
| ---: | --- |
| `0` | Success, help, or version output. |
| `2` | Command-line, config-schema, ABI-schema, skip-list, entry-selection, or overwrite-protection error. |
| `3` | Malformed input, unsupported/invalid lowering, strict-mode approximation, or no functions left to translate. |
| `4` | Input/config/manifest I/O or project-generation/publication failure. |
| `5` | Internal failure, including allocation failure. |

## Generate and build a title project

```sh
build/porpoise path/to/asm --output generated/title --abi title-abi.json
```

On Windows, invoke `build/porpoise.exe` from the MinGW64 environment. See [INPUT_FORMAT.md](docs/INPUT_FORMAT.md) for the accepted annotated assembly dialect.

Generated projects resolve this Meson dependency:

```meson
dependency('libPorpoise', fallback: ['libPorpoise', 'libporpoise_dep'])
```

Provide either an installed `libPorpoise` dependency or a checkout at `generated/title/subprojects/libPorpoise` that exports `libporpoise_dep`. Porpoise Tool deliberately creates no wrap file and chooses no library revision.

The currently evolving checkout also defaults its own `build_target` option to `gc`. When using that version as a host subproject, select the host explicitly during setup, for example `-DlibPorpoise:build_target=linux` or `-DlibPorpoise:build_target=win64`. Treat that option as version-sensitive integration surface; an installed dependency may expose a different contract.

Then build the generated project:

```sh
meson setup generated/title/build generated/title -DlibPorpoise:build_target=linux
meson compile -C generated/title/build
```

Every successful generation provides the `porpoise_lifted` static library and the Meson dependency override `porpoise-generated`. An executable named `porpoise_title` is added only when:

- `--entry` names a translated, unskipped input function; or
- exactly one unskipped function is declared as `.fn main, global`.

The executable exports `DolphinMain`, initializes the `libPorpoise` adapter once, and invokes the lifted entry. It never runs a transpiled console `__start`. Without an entry, the generated static library remains usable by another host target.

Generation happens in a sibling staging directory. Failed parsing, lowering, or writing leaves the requested destination untouched. With `--force`, the previous destination is moved to a backup only during publication and restored if publication fails.

## Measured instruction report

`porpoise-report.json` is deterministic for the same inputs and options. It records input-to-generated file mappings, functions, annotated data words, every translated instruction, approximations, diagnostics, and summary counts.

| Status | Meaning |
| --- | --- |
| `lowered` | The opcode registry emitted C for the accepted operand form. This is not a whole-ISA or whole-opcode proof. |
| `host-equivalent-no-op` | The registry intentionally emitted no PPC state change for the host model. |
| `approximate` | The emitted host operation does not reproduce exact hardware semantics. It warns normally and fails under `--strict`. |
| `unsupported` | No supported lowering exists. Translation fails and no staged project/report is published. |

Each instruction also has a `semantic_test` boolean. `false` means the registry has no dedicated semantic test for that entry; it must not be interpreted as verified. Successful reports normally have an `unsupported` count of zero because unsupported instructions abort publication.
